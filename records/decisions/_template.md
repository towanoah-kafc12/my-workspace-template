# 決定事項の記録ルール

## 記録する条件

複数の作業で今後も前提になる決定と、その理由を記録します。

次の情報はここへ記録しません。

- 一つの作業内だけで完結する判断
- 対象リポジトリ内だけで有効な実装判断
- 現在の状態だけを示す情報
- 後続作業の前提にならない一時的な選択

作業固有の判断は対象の`work/`または`repos/`内に残します。現在の状態として長期的に参照する情報は`knowledge/`へ置きます。

## 記載形式

領域ファイルへ次の形式で追記します。項目を管理するためのIDやfrontmatterは付けません。

```markdown
## タイトル

- 決定日: YYYY-MM-DD
- 状態: 有効
- 決定:
- 理由:
- 影響範囲:
```

比較した案、制約、関連ファイルへのリンクは、判断の理解に必要な場合だけ追加します。

## 記載例

```markdown
## 作業完了後の保管先

- 決定日: 2026-07-29
- 状態: 有効
- 決定: 完了した作業フォルダはwork/archiveへ移す
- 理由: 進行中の作業と分けつつ、成果物を作った過程はワークスペース内に残すため
- 影響範囲: work配下のすべての作業
```

## 決定を変更または廃止する場合

- 以前の記録は削除しない
- 以前の記録の状態を`変更`または`廃止`にする
- 新しい決定がある場合は別の項目として追記し、双方へリンクを付ける
- 変更日と、変更または廃止した理由を以前の記録へ追記する

## knowledgeへ反映する基準

決定によって、PJで長期的に参照する現在の情報が変わる場合だけ`knowledge/`を更新します。

- 決定の理由や比較経緯は`records/decisions/`に残す
- 現在の構成、前提、用語などは`knowledge/`へ反映する
- 同じ説明を両方へ複製せず、必要な場合はリンクでつなぐ
- 反映先がなく、長期参照する必要もない場合は、decisionを転記するためだけにknowledgeファイルを作らない

## ファイルを分ける基準

最初は`project.md`へ記録します。次の状態になった領域だけ、`aws.md`や`database.md`などの領域ファイルへ分けます。

- その領域だけを独立して読む機会が増えた
- その領域だけを独立して更新することが増えた
- 関係のない情報まで読む負荷が大きくなった
- ユーザからの指示

一つの領域内に互いにほぼ独立した関心事が育った場合は、その領域だけをディレクトリ化します。単純な行数や件数では分けません。

`records/open/`でも、原則として同じ分類軸を使います。ただし、記録がない側に空ファイルを作る必要はありません。
